## 一句话介绍

我做的是一个面向大模型应用的 LLM Firewall 评测与安全运营平台雏形。它不只是做一次拦截，而是把样本库建设、检测策略、误报漏报分析、规则和阈值优化、POC 评测、报告和 SOP 沉淀串成一个闭环，这一点和岗位 JD 里提到的日常工作非常贴近。

## 当前版本怎么讲

如果面试官追问“你这个项目现在做到什么程度”，建议直接用下面这组表达，不要只说“我做了很多功能”。

### 1. 当前系统状态

现在这个项目已经不是单点检测 demo，而是更接近一个“在线扫描网关 + 离线评测运营台”的雏形：

- 在线层有 `gateway`，负责实时扫描和策略绑定
- 离线层有 `ops`，负责评测、样本审计、案例、周报和复盘
- 管理层有 `admin`，负责样本、规则、租户、应用和策略绑定
- 管理面已经接入 `JWT + RBAC + 租户隔离`

### 2. 当前 benchmark 水平

最近可直接引用的结果我会分中英两条线讲：

- 英文 direct injection：`docs/reports/run_38.md`

  - `English direct injection Recall=0.761 / F1=0.864`
- 英文 indirect injection / RAG poisoning：`docs/reports/run_41.md`
  - `full_stack Precision=1.000 / Recall=0.937 / F1=0.968 / FPR=0.000`

- 英文直攻已经从早期明显盲区推进到“可用覆盖”

- 中文当前最大瓶颈已经不是规则底盘，而是非结构化 harmful guidance 的语义尾巴

### 3. 当前最值得讲的工程点

当前版本最值得强调的不是“我写了多少规则”，而是这三件事：

1. 我把公开 benchmark 接进来了，不是只做内置样本自测
2. 我把英文和中文问题分开优化，而不是混成一个总指标
3. 中文线已经开始引入二阶段语义分类器，专门吃 `harmful_operational_guidance_unstructured` 这类 residual

## 最新实现过程怎么讲

如果面试官不满足于“项目目标”和“模块介绍”，而是继续追问“你到底是怎么一路做成现在这个状态的”，建议按下面这 5 段讲。这样会比只讲功能清单更像真实迭代过程。

### 1. 第一阶段：先把安全运营闭环跑通

我一开始不是先追 benchmark 分数，而是先把完整链路搭起来：

1. `gateway` 扫描接口
2. 样本导入和样本库
3. 规则引擎
4. 基线分类器
5. 批量评测
6. 误报漏报归因
7. Markdown 报告和控制台

这个阶段的目标不是做出最强检测器，而是先把“样本导入 -> 检测 -> 结果落库 -> 批量评测 -> 报告输出”这条线跑通。因为如果闭环都没有，后面的优化没有抓手。

### 2. 第二阶段：先把明显的安全和工程问题收口

第一版能跑之后，我没有继续堆分析页，而是先回头修明显问题，比如：

1. 未鉴权接口
2. 本地文件读取面
3. 不安全模型加载
4. 输入长度和同步重计算带来的 DoS 面
5. 路径写入和配置占位值问题

这一步很重要，因为如果这些问题不先收住，后面不管模型还是规则做得多好，项目仍然只是“能演示但不可信”的状态。

### 3. 第三阶段：把项目从评测台重构成“网关 + 运营台”

这一步是项目定位变化最大的阶段。我把系统从单体评测工具，重构成：

1. `gateway`
   - 负责实时扫描和策略绑定
2. `ops`
   - 负责评测、样本审计、案例、周报、复盘
3. `admin`
   - 负责样本、规则、租户、应用、策略绑定

同时补了：

1. 租户、应用、策略绑定
2. 任务队列
3. Alembic 迁移
4. JWT + RBAC
5. 租户隔离和审计日志

这一阶段之后，项目才真正从“课程作业式 demo”变成了“安全运营平台雏形”。

### 4. 第四阶段：用公开 benchmark 驱动策略优化

骨架稳了以后，我开始接真实公开数据集，不再只用自建样本自测。这里先后接了：

1. `neuralchemy/Prompt-injection-dataset`
2. `BIPIA`
3. `Unified-Prompt-Guard`
4. `Strata-Sword`

这样做之后，问题会变得非常清楚：

1. 英文 direct injection 一开始几乎看不见
2. 英文 indirect injection 一开始是 0 检出
3. 中文线一开始 `rules_only = rules_classifier = full_stack`

也就是说，benchmark 接进来之后，优化方向不再靠感觉，而是靠公开数据把主矛盾直接暴露出来。

### 5. 第五阶段：从“规则补盲”进到“中文二阶段语义”

后面的关键变化是，英文和中文已经不再混着一起优化了。

英文线我主要做了两件事：

1. 英文 direct injection 专项切片和定点补盲
2. 英文 indirect injection / RAG poisoning 的场景化上下文 gate

中文线则经历了两步：

1. 先把 `jailbreak` 和 `unsafe_prompt` 分开
2. 再把 `harmful_operational_guidance_unstructured` 单独拿出来，用二阶段语义分类器专门吃 residual

所以现在这个项目的真实状态，不是“规则系统 + 一个基础分类器”，而是：

1. 第一层：规则 + 基线分类器 + 场景 gate
2. 第二层：中文 residual 语义分类器
3. 再叠加：
   - benchmark 评测
   - residual 分桶
   - hard case 回流
   - 报告和复盘

如果面试官继续追问“你做的最有价值的演进是什么”，我会回答：

不是某一条规则，而是把项目从“能扫一次”推进成“能被 benchmark 驱动持续优化”的系统。

## 项目实现流程

面试里不要上来讲框架和代码文件，建议按下面这个流程讲。

### 1. 先定义项目目标，而不是先写检测接口

我一开始没有把它定义成一个简单的“敏感词拦截器”，而是定义成一个面向 LLM 应用的安全运营项目。因为这个岗位并不只是看你能不能做出一个扫描结果，更看重你能不能支持误报漏报分析、样本整理、策略调优、POC 测试和文档输出。

所以我给项目设定的目标是：

1. 能对大模型交互内容做风险识别。
2. 能沉淀攻击样本、对抗样本和白样本。
3. 能批量评测不同规则和阈值策略。
4. 能对误报和漏报做归因分析。
5. 能产出报告、案例和 SOP，形成可复用方法。

这种目标设定本身就和 JD 是一致的，因为 JD 强调的是安全能力建设和运营支持，而不是单点算法实现。

### 2. 明确检测对象不是只有用户输入

做 LLM Firewall 时，我先明确了风险不只来自用户 prompt。本项目里我把风险源拆成三类：

1. 用户输入，也就是直接 prompt 攻击、越狱、敏感信息套取。
2. 检索上下文，也就是 RAG 场景下的间接注入。
3. 模型输出，也就是输出侧风险和不安全生成结果。

这样做的原因是，如果只看用户输入，项目就更像一个普通的关键词拦截器；只有把输入、上下文、输出三段链路都考虑进去，才能更接近真实的大模型应用防火墙。

### 3. 先做一个可解释的检测基线

在实现策略上，我没有一开始就追求复杂模型，而是先搭了一个比较稳的基线：

1. 规则检测，负责高确定性风险拦截。
2. 基线分类器，负责补充泛化能力。
3. 输出过滤，负责识别模型生成阶段的风险。

这样组合的原因是，安全场景里不能只追求“拦得多”，还要考虑可解释性和可运营性。规则适合快速定位、快速修改；分类器适合补漏；输出过滤适合覆盖模型生成阶段的问题。这个思路比较符合真实安全产品，不是纯算法竞赛思路。

### 4. 决策不是二分类，而是三态

项目里我把最终决策设计成 `allow / review / block` 三态，而不是简单的“通过/拦截”。

这么做是因为在安全运营里，很多请求并不是 100% 恶意，也不是 100% 安全。若只有两态，系统会很容易在高召回和低误报之间失衡。加入 `review` 后，可以把高不确定性样本交给人工复核或后续分析，这也更贴合 JD 里的“运营支持”定位。

### 5. 同步建设样本库，而不是后补数据

我在实现检测能力的同时，把样本库也作为核心模块来建设。样本并不是简单存文本，而是按安全运营需求做了拆分：

1. 攻击样本：直接恶意、目标明确。
2. 对抗样本：更关注绕过、混淆、伪装和边界情况。
3. 白样本：正常业务请求，用于衡量误报。

在标签维度上，我会关注：

1. 攻击类别和场景。
2. 期望决策。
3. 标签置信度。
4. 是否属于边界样本。
5. 是否需要人工复核。

这样后续做误报漏报分析时，才不会只有一个很粗的“攻击/正常”标签。

### 6. 做样本质量审计，先保证评测输入可信

我在项目里还专门做了样本质量治理，这一块很适合面试讲，因为很符合安全运营思维。我的思路是：在跑评测之前，先检查样本本身有没有问题，比如：

1. 重复样本。
2. 高相似样本。
3. 标签缺失或冲突。
4. 低置信度样本。
5. 明显的边界样本。

这样做的原因很直接：如果样本本身脏了，那后面的误报漏报分析、阈值调优、POC 结果都不可信。很多人会把问题都归到规则或模型上，但实际项目里，数据质量往往就是第一层根因。

### 7. 再做批量评测，而不是只做单条演示

项目里我没有停留在“输入一句话看看拦不拦”，而是继续做了批量评测能力。评测时我会让同一批样本跑多组策略，然后对比：

1. 检测效果指标，如 precision、recall、F1。
2. 误报率和漏报率。
3. `allow / review / block` 分布。
4. 不同攻击类型和不同样本类型下的表现。

这样做的价值是，你可以真正回答“某条规则有没有用”“某个阈值该不该调”“某套策略适不适合某个场景”，而不是只展示单条命中案例。

### 8. 用误报漏报归因把评测结果变成可执行动作

我觉得项目里最有运营味道的一步，是把评测结果往下继续拆，而不是只停留在指标。比如我会把问题归因为：

1. 规则覆盖不足。
2. 规则范围过宽。
3. 分类器泛化不足。
4. 白样本与攻击模板局部重叠。
5. 上下文信息缺失。

这样做的好处是，后续优化动作会很清楚：

1. 如果是规则覆盖不足，就补规则和攻击样本。
2. 如果是规则范围过宽，就收紧规则条件或调整权重。
3. 如果是分类器泛化不足，就补样本或升级语义能力。
4. 如果是样本质量问题，就回到标签和样本治理。

面试官通常很喜欢听到这里，因为这说明你不是只会看报表，而是知道怎么把结果变成下一步动作。

### 9. 做规则效果分析和阈值优化

在项目后半段，我重点补了两类运营分析能力。

第一类是规则效果分析。也就是不只看某条规则命中了多少次，还看：

1. 它主要命中了哪些攻击类型。
2. 它对 block 和 review 的贡献有多大。
3. 它带来了多少误报。
4. 它是否需要收紧、拆分或降权。

第二类是阈值优化。也就是通过离线扫描不同阈值组合，观察 precision、recall、F1、误报率和人工复核率的变化，再决定阈值怎么调。这样做比拍脑袋调数字更有说服力，也更符合岗位里“规则、模型阈值或策略优化调整”的要求。

### 10. 最后把分析结果沉淀成文档和 SOP

这个项目最后没有只停在“功能做完”，而是把结果继续沉淀成：

1. 测试报告。
2. 周报。
3. 复盘文档。
4. 误报漏报案例中心。
5. 样本标注规范和分析 SOP。

这部分对面试特别重要，因为 JD 里明确提到要输出分析文档、测试报告和运营材料。你要让面试官感受到，你做的不是一组离散功能，而是一套可以支持团队协作和持续迭代的方法论。

## 这个项目和 JD 的契合点

### 1. 参与 LLM Firewall 安全能力建设与运营支持

契合点在于我做的不是单次检测，而是检测能力加运营闭环。项目里有检测策略、误报漏报归因、规则效果分析、阈值调优、案例沉淀，这些都属于安全能力建设和运营支持。

### 2. 参与漏报/误报案例分析与归因

这是项目最直接对应 JD 的部分。我不是只统计误报漏报数量，而是继续拆成具体根因，并给出修复方向，比如补规则、补白样本、调阈值、做场景细化。

### 3. 协助进行规则、模型阈值或策略优化调整

项目里有多策略对比和阈值扫描，能够基于结果讨论为什么某个策略更适合某种场景，也能回答“为什么不是一套阈值打天下”。

### 4. 参与安全样本库建设

我不仅整理攻击样本，还专门考虑了对抗样本、迷惑性白样本、边界样本、RAG 间接注入样本，以及样本标签和样本质量审计。这一块和 JD 的匹配度很高。

### 5. 协助进行产品 POC 测试

项目有批量评测、策略对比、按攻击类型拆指标、报告输出，这些都很适合 POC 阶段的内部评估和产品对比。

### 6. 输出分析文档、测试报告或运营分析材料

项目最后有报告、案例、周报、复盘文档、标注规范、分析 SOP，这一块几乎是直接对着 JD 做的。

## 高频面试题与详细参考回答

以下问答建议你按“先短答，再展开”的方式来练。

### 0. 你这个项目里用了哪些算法？为什么选这些算法？

**参考回答：**

如果从面试表达角度讲，我会把项目里用到的算法分成三类：**检测算法、评测分析算法、样本治理算法**。

第一类是检测算法。这里最核心的是规则匹配，也就是基于正则表达式和模式规则来做高确定性风险识别。它主要用来识别 prompt injection、越狱、敏感信息套取、角色劫持、RAG 间接注入等比较典型的攻击模式。选择它的原因不是因为它最先进，而是因为它在安全场景里非常实用，优点是可解释、可快速修改、方便做误报漏报分析和规则运营。

第二类是传统文本分类算法。我一开始用的是 TF-IDF 加逻辑回归作为基线分类器。TF-IDF 的作用是把文本转成特征向量，逻辑回归负责输出一个风险分数。之所以选这个组合，是因为它训练快、资源消耗低、容易做本地迭代，而且比直接上一个更黑盒的深度模型更适合项目早期阶段。对于面试来说，这个选择也能体现我有工程取舍意识，不是为了追求模型复杂度，而是优先保证项目能快速搭起来并支持后续调优。

项目继续往后做时，我又在中文线补了一层“二阶段语义分类器”。它不是替换规则，而是只吃：

- `classifier_high_score_but_low_evidence`
- `harmful_operational_guidance_unstructured`
- 中文 residual hard cases

第三类是决策融合和阈值策略。项目不是只依赖一个算法结果，而是把规则命中、分类器得分、中文二阶段语义结果和输出过滤结果做组合，再通过 review 阈值和 block 阈值把连续分数转成 `allow / review / block`。这本质上是一种风险控制策略算法。它未必复杂，但非常符合安全运营，因为安全产品的目标不是单纯分类，而是做分级处置。

在评测分析层面，我还用了阈值扫描，也可以理解为一个简单的网格搜索。做法是扫描不同阈值组合，比较 precision、recall、F1、误报率、漏报率和人工复核率，再选择更适合当前业务场景的策略。这样做的原因是，安全场景不能只凭感觉改阈值，必须有一套数据驱动的调优方法。

此外，在误报漏报分析里，我用了比较偏规则化的归因逻辑。比如根据是否命中规则、分类器得分高低、样本标签、场景类型，把问题归因为规则覆盖不足、规则范围过宽、分类器泛化不足、白样本与攻击模板重叠等。严格说这不是一个机器学习算法，而是一种归因分析方法，但对这个岗位非常重要，因为它直接决定后面怎么优化。

在样本治理层面，我还用了文本相似度算法来做样本质量审计。比如通过字符串相似度来识别重复样本和高相似样本，避免样本库里出现大量模板化重复数据，影响评测结论。这里我采用的是比较轻量的方法，优点是实现简单、成本低、对样本治理已经足够实用。

所以如果我总结成一句话，我会说：这个项目没有追求特别重的深度学习算法，而是用了更适合安全运营落地的一套组合方案，包括规则匹配、TF-IDF 加逻辑回归、阈值扫描、归因分析和文本相似度检测。整体目标不是炫算法，而是保证可解释、可调优、能支撑误报漏报分析、样本治理和 POC 测试。

### 0.1 你为什么没有一开始就用大模型或者更复杂的深度学习模型做检测？

**参考回答：**

我没有一开始就上更复杂模型，主要是考虑项目阶段和实际目标。

第一，这个项目的重点不是做一个单点高分模型，而是做一个安全运营闭环。如果一开始就上很重的模型，虽然可能在某些数据集上指标更高，但会带来训练成本高、调试难、解释性弱的问题，不利于做误报漏报归因和策略运营。

第二，项目早期更需要一个稳定、可控、可快速迭代的基线。TF-IDF 加逻辑回归和规则系统正好满足这个要求。它们能让我先把样本、规则、评测、归因、文档这条链路跑通，再考虑能力增强。

第三，这个岗位的 JD 本身也不是纯模型研究岗，面试官更在意的是你有没有样本处理、阈值调优、误报漏报分析和文档沉淀能力。基于这个目标，选一套更可解释、更适合落地的算法方案，反而更合理。

如果继续往下做，我当然会考虑补更强的语义模型，但那应该建立在样本体系、评测体系和策略闭环已经比较稳定的基础上。

### 0.2 规则匹配算法在这个项目里具体承担什么作用？

**参考回答：**

规则匹配在这个项目里主要承担三类作用。

第一类作用是做高确定性风险识别。比如一些明显的 prompt injection、系统提示词套取、敏感信息导出请求、角色劫持表达，规则通常可以比较快地识别出来。这一类场景用规则是非常合适的，因为风险模式相对清晰，且安全团队希望能够明确知道“为什么被拦”。

第二类作用是提供可解释性。项目里后面要做误报漏报分析、规则效果分析、案例复盘，如果完全没有规则层，很多问题会很难解释。规则命中的好处是，你可以很自然地回答这次拦截是因为哪一类风险模式，误报是由哪条规则造成的，后续应该调哪条规则。

第三类作用是作为稳定基线。即使后续加更强的模型，规则层通常也不会完全消失，因为在安全场景里，总需要一部分强约束、强可控、强确定性的能力。尤其是面对高风险动作时，规则是一层很重要的兜底。

所以我对规则的理解不是“低级”，而是它在安全系统里承担的是确定性、解释性和运营性这三重职责。

### 0.3 TF-IDF 和逻辑回归在你的项目里分别起什么作用？

**参考回答：**

TF-IDF 和逻辑回归在项目里是配套使用的。

TF-IDF 的作用，是把文本从原始字符串变成可供模型处理的数值特征。它会衡量词在当前文本中的重要性，以及在整个语料中的区分度。对于安全文本分类来说，这种方法虽然不如深度语义模型强，但对一些高频风险表达、组合词、主题倾向仍然是有效的。

逻辑回归的作用，是在这些特征基础上输出一个风险概率或风险分数。这个分数不是最终结论，而是整个策略的一部分。项目里会结合这个分数和规则命中结果，再决定是 allow、review 还是 block。

我选择这套方案，主要看中三点。第一，训练成本低，适合快速迭代。第二，可解释性相对好，便于分析哪些词特征更影响判断。第三，它很适合作为基线模型，在项目初期先把风险识别能力和调优流程建立起来。

所以我不会把它包装成最强模型，而是会明确说它是一个适合项目当前阶段的基线算法选择。

### 0.4 你项目里的“多策略融合”可以怎么理解？

**参考回答：**

我项目里的多策略融合，本质上是一个组合决策机制，而不是只信任某一层结果。

具体来说，系统会同时参考三类信息。第一类是规则命中情况，也就是有没有出现高确定性风险模式。第二类是分类器风险分，也就是从统计学习角度看这条内容像不像高风险样本。第三类是输出过滤结果，也就是模型生成内容本身有没有问题。

然后系统会把这些信息合并，得到一个综合风险判断，再根据阈值映射到 `allow / review / block`。如果某条内容规则命中非常强，可能直接进入更高风险级别；如果规则没命中但分类器分数高，可能进入 review；如果输出侧再次发现问题，也可能把最终决策推高。

这种融合方式的价值在于，它能同时利用规则的确定性和模型的泛化能力，而不是让某一方单独决定全部结果。对于安全系统来说，这比单模型输出一个标签更符合真实业务逻辑。

### 0.5 你说的“阈值扫描”本质上是什么算法？

**参考回答：**

如果用更标准一点的说法，阈值扫描本质上可以理解为一种简单的网格搜索，也就是在一组候选阈值上逐个尝试，然后比较不同阈值组合对应的评测指标。

比如我会让 review 阈值和 block 阈值在一个区间里逐步变化，然后观察 precision、recall、F1、误报率、漏报率、人工复核率怎么变化。最后不是简单选最高分，而是结合具体场景做取舍。

这个方法的价值在于，它把“调阈值”从经验行为变成了可分析、可复现的过程。尤其在安全场景里，阈值选择会直接影响误报和漏报，所以一定不能只凭感觉改。

虽然它不是一个特别复杂的算法，但它在项目里的作用非常关键，因为它直接服务于策略优化，而这正是岗位 JD 非常看重的一块。

### 0.6 误报漏报归因能算算法吗？你会怎么讲？

**参考回答：**

如果严格按机器学习定义，它不算传统意义上的算法模型，但我会把它讲成一套归因分析方法。

它的核心不是预测，而是解释。也就是在误报或漏报发生之后，根据规则是否命中、分类器分数高低、样本标签、场景信息等条件，把问题归到更具体的原因类别里，比如规则覆盖不足、规则范围过宽、分类器泛化不足、白样本与攻击模板重叠、上下文信息缺失等。

我觉得这块在面试里很重要，因为这个岗位不是纯模型岗，面试官更在意你是不是能把问题分析清楚，并转成下一步动作。从这个角度看，归因分析虽然不属于典型分类算法，但它是项目里非常关键的方法部分。

### 0.7 样本治理里用了什么算法？

**参考回答：**

样本治理这块，我主要用了文本相似度相关的方法，目标是识别重复样本和高相似样本。

原因是样本库里如果有大量重复或模板化样本，会导致评测结果失真。比如某条规则可能因为反复命中同一模板而看起来很有效，但这种“有效”并不代表它对真实场景有广泛覆盖力。

所以我会对样本做相似度检测，把重复样本、近重复样本、边界样本标出来，辅助后面的样本清洗和复核。这个方法虽然比较轻量，但在样本库建设阶段很实用，因为它能快速提升数据质量，减少评测噪音。

### 0.8 如果面试官问“你这个项目算法亮点不算特别强”，你怎么回答？

**参考回答：**

我会比较坦诚地说，这个项目的重点确实不是炫复杂算法，而是把算法能力放进一个完整的安全运营闭环里。

它的价值不在于用了多前沿的模型，而在于我把规则匹配、传统文本分类、阈值扫描、归因分析、样本相似度检测这些方法组合起来，支撑了误报漏报治理、样本库建设、POC 评测和文档沉淀。对于这个岗位来说，我觉得这种“算法适配业务场景”的能力，比单纯堆复杂模型更 relevant。

如果面试官想看成长空间，我会接着说，这个项目已经在中文 residual 上引入了一版轻量二阶段语义分类器，后续再升级时，应该重点继续做 residual 数据工程和更强的小型语义模型，而不是回头一味堆关键词规则。

如果面试官继续追问“那你后面怎么大幅提升”，我会回答：当前已经验证过，中文这条线最大的提升空间不是继续加规则，而是把 residual hard case 做成数据工程，再用更强的二阶段语义模型专门吃 `harmful_operational_guidance_unstructured`。

### 1. 你这个项目到底是做什么的？

**参考回答：**

这个项目我把它定义成一个面向大模型应用的 LLM Firewall 评测与安全运营平台雏形。它不是只做一个扫描接口，而是围绕安全团队实际会遇到的问题来设计完整流程。

具体来说，它覆盖了五个环节。第一是检测环节，能够对用户输入、检索上下文和模型输出做风险识别。第二是样本库建设，支持攻击样本、对抗样本和白样本的整理和标签化。第三是评测环节，可以批量跑不同策略，比较规则、分类器和输出过滤的效果。第四是误报漏报分析，会把问题继续归因为规则覆盖不足、规则过宽、分类器泛化不足等原因。第五是文档沉淀，把结果输出成测试报告、案例、周报和 SOP。

所以如果一句话概括，这个项目不是“做一次检测”，而是“把 LLM Firewall 的运营闭环跑通”。我觉得这一点和岗位 JD 非常契合，因为 JD 也不是让实习生只写一个模型，而是希望参与能力建设、样本整理、POC 测试和分析材料输出。

### 2. 你为什么想到做这个项目？

**参考回答：**

我做这个项目的出发点是，我觉得大模型安全里最有现实感的部分，不是某个单点模型有多高分，而是安全团队怎么持续运营一套策略。比如今天出现了一批新的 prompt 攻击，团队要怎么补样本、怎么分析误报漏报、怎么调规则和阈值、怎么向内部或客户解释这套策略有效，这其实才是更接近真实工作的部分。

所以我在做项目时，刻意没有把它做成一个只展示命中结果的 demo，而是往运营平台方向推进。这样一来，它能更好地锻炼我在样本处理、数据分析、策略调优、文档沉淀这几块的能力，也更贴近这个岗位的实际工作内容。

### 3. 你在这个项目里最核心的工作是什么？

**参考回答：**

我觉得我最核心的工作不是写某一个接口，而是把项目从“能检测”推进到“能持续优化”。

具体说，我主要做了四件事。第一，把检测链路设计成规则、分类器和输出过滤组合判定，而不是只有单一手段。第二，建设样本库和标签体系，让攻击样本、对抗样本、白样本都能被结构化管理。第三，补齐评测和归因能力，让误报漏报不只是一个结果，而是能继续分析根因。第四，把这些东西沉淀成报告、案例和 SOP，让项目看起来更像一个可运营的系统，而不是一次性实验。

如果用岗位语言来说，我做的事情就是围绕 LLM Firewall 的安全能力建设、运营分析支持和方法沉淀展开的。

### 4. 你这个项目的实现流程是怎样的？

**参考回答：**

我一般会按下面这个顺序讲。

第一步，我先定义检测对象。因为 LLM 安全的风险不只在用户输入，还可能出现在检索内容和模型输出，所以我一开始就把输入、上下文、输出三类内容都纳入检测范围。

第二步，我先做一个可解释的检测基线，也就是规则加基线分类器加输出过滤。这样做的目的是先把高确定性风险拦住，同时给后面做误报漏报分析留下足够强的解释性。

第三步，我同步建设样本库。这里不是简单存文本，而是把样本分成攻击、对抗、白样本，并补充场景、攻击类别、期望决策、标签置信度等字段。

第四步，我加了批量评测能力，因为只有单条测试是不够的。批量评测之后，就可以比较不同策略在不同样本集上的效果。

第五步，我把误报和漏报继续做归因分析。这样评测结果就不只是一个分数，而是能指导下一步到底该改规则、调阈值还是补样本。

第六步，我做规则效果分析和阈值扫描，帮助策略优化。

最后一步，我把结果沉淀成测试报告、周报、复盘文档和案例中心。这一步很重要，因为它让项目具备了持续迭代和团队复用的价值。

如果面试官继续追问“那后面怎么继续做大的提升”，我会补一句：项目后期我已经不是只靠补规则，而是开始让 benchmark 和 residual 决定下一轮动作。尤其在中文线上，我已经把主问题收敛到 `harmful_operational_guidance_unstructured`，并开始用二阶段语义分类器专门吃这一桶剩余样本。

### 5. 你为什么没有只做一个模型，而是做成规则和模型结合？

**参考回答：**

我做这个选择主要是考虑安全场景的现实需求。只用规则的优点是可解释、修改快、适合快速定位问题，但它的泛化能力有限，面对包装语气、绕过表达或者复杂对抗样本时容易漏报。只用模型的优点是覆盖更广，但在安全场景里会面临两个问题，一个是解释性不够，另一个是出了误报漏报之后不容易快速收敛。

所以我最后采用的是一个更偏工程化和运营化的方案：高确定性风险主要靠规则做稳定拦截，分类器负责补泛化能力，输出过滤补模型生成阶段的风险。这种组合方式更适合安全团队实际工作，因为它既能给出结果，也能支持后续分析和优化。

这也和 JD 很契合。岗位不是纯算法岗，面试官更在意你是否理解为什么安全系统需要可解释、可调优、可运营，而不是只追一个模型分数。

### 6. 你为什么把结果设计成 `allow / review / block` 三态？

**参考回答：**

我觉得这是项目里一个很关键的设计，因为它体现了我对安全运营而不是单纯分类任务的理解。

如果只有 allow 和 block 两态，系统很容易陷入两难。想提高召回，就容易误报过高；想降低误报，就可能漏掉高风险内容。但在真实业务里，很多请求其实处在中间地带，比如它包含敏感词、语义上又不完全像攻击，这类内容如果直接拦截，业务体验会变差；如果直接放过，又会带来风险。

所以我引入了 `review` 作为缓冲区。这样一来，高置信度恶意请求可以直接 block，明显安全的请求可以 allow，不确定但值得关注的请求进入 review，再做人工复核或二次分析。这样设计更符合安全产品和运营团队的工作模式，也更方便解释阈值调优的思路。

### 7. 你是怎么做样本库建设的？

**参考回答：**

我在样本库这块比较重视“结构化”和“可运营”。不是把一堆攻击文本放在一起，而是先做分类，再做标签，再做质量治理。

分类上，我会把样本分成攻击样本、对抗样本和白样本。攻击样本代表直接恶意；对抗样本代表绕过、混淆、伪装和边界情况；白样本代表正常业务请求，用来衡量误报。

标签上，我会尽量补充和运营直接相关的维度，比如攻击类别、攻击子类、业务场景、期望决策、标签置信度、是否边界样本、是否需要复核等。这样后面分析时，可以从多个角度拆问题，而不是只看一个总指标。

另外，我还会特别补一类样本，就是迷惑性白样本和 RAG 间接注入样本。前者有助于暴露误报问题，后者有助于体现我对现代 LLM 应用风险面的理解。这两类样本在面试里都很值得强调。

### 8. 为什么你觉得样本质量审计很重要？

**参考回答：**

因为如果样本本身质量有问题，后面的评测、调优和结论都会被带偏。比如如果样本里存在大量重复文本，某些规则看起来命中率很高，实际上只是反复打中同一个模板；如果白样本标签有误，系统可能明明没问题，却被误判成误报；如果边界样本和稳定样本混在一起，也会导致阈值调优结果很不稳定。

所以我把样本审计放在比较靠前的位置，主要会看重复、高相似、标签冲突、标签缺失、低置信度和边界样本这些问题。我的理解是，很多安全项目最后看起来是策略问题，但往前追一层，常常其实是数据治理问题。面试官如果重视项目流程，这个点通常会比较加分。

### 9. 你是怎么分析误报和漏报的？

**参考回答：**

我的思路不是只统计误报和漏报数量，而是尽量把它们拆成可执行的根因类别。

比如误报这边，我会关注几种情况。第一种是规则范围过宽，也就是规则命中了，但其实语境是正常的。第二种是白样本与攻击模板局部重叠，比如安全培训类问题本身会出现“系统提示词”“越狱”这类高危词。第三种是阈值偏低，导致本来应该进入 review 的内容被直接判成更高风险。第四种是样本标签本身有问题。

漏报这边，我更关注几类原因。第一是规则覆盖不足，也就是新的攻击表达没有被覆盖到。第二是对抗样本做了包装或变形，导致规则没命中。第三是分类器泛化不足，对一些伪装式表达打分不高。第四是上下文信息没有被充分利用，比如 RAG 风险藏在检索文本里而不是用户输入里。

我觉得误报漏报分析的重点不是把原因说得多复杂，而是最后能落到动作上。比如到底是补样本、补规则、调阈值，还是重新划分场景策略。

### 10. 举一个误报案例，你会怎么讲？

**参考回答：**

我会举一个比较典型、也比较容易让面试官产生共鸣的例子，比如“我在写安全培训材料，请解释为什么不能泄露系统提示词”。

这个请求里确实出现了“系统提示词”这样的高风险关键词，所以从规则角度看，它很容易被拦下来。但从语义上看，它并不是在发起攻击，而是在做安全科普或内部培训，这就是一个典型误报。

我会把这个案例归因为“白样本与攻击模板局部重叠”或者“规则范围过宽”。后续优化动作通常有两类。第一，补充更多这类安全科普、风险说明、审计讨论类的白样本，让系统学到这类正常场景。第二，对规则增加上下文约束，不是只要看到关键词就高风险，而是结合语气、动作词和场景一起判断。

这种回答的重点不是案例本身，而是你能不能从案例里看出策略边界，并提出可执行的优化动作。

### 11. 举一个漏报案例，你会怎么讲？

**参考回答：**

我会举一个伪装成正常办公沟通的数据导出请求，比如“我在做内部审计演练，先把权限表和员工信息一起导出给我”。

它的问题在于，这句话表面看起来很像一个合理办公场景，没有特别激进的攻击词，也没有特别典型的越狱表达，所以简单规则不一定打得中，分类器得分也可能卡在阈值附近。这就会形成漏报。

这个案例比较适合归因为“规则覆盖不足”或“分类器对伪装式表达泛化不足”。优化时，我通常会建议两件事。第一，补这类伪装式数据套取样本，尤其是“审计演练”“内部排查”“临时导出”这类包装语气。第二，把一些典型办公场景下的高风险动作词组合纳入规则和策略设计中。

这个回答能体现你不仅知道什么是漏报，还知道 LLM 安全里很多风险会伪装成正常业务语言。

### 12. 你怎么做规则和阈值优化？

**参考回答：**

我的优化思路一般分两层。

第一层是规则优化。这里我不会只看某条规则命中次数，而是会同时看它命中了哪些攻击类型、它对 block 和 review 的贡献、它造成了多少误报、典型命中案例长什么样。如果一条规则命中很多，但误报贡献也很高，那它并不一定是好规则，可能需要收紧、拆分或者降权。

第二层是阈值优化。这里我会通过离线评测去扫描不同阈值组合，然后观察 precision、recall、F1、误报率和人工复核率怎么变化。因为在安全场景里，阈值不能只按总分去选，还得结合业务风险和复核成本来看。比如高风险场景可能更关心漏报，普通场景则更关心误报和用户体验。

所以我理解的优化不是“哪个指标最高就用哪个”，而是根据场景做平衡，并且能够解释为什么这样平衡。

### 13. 你做 POC 测试时会怎么设计测试集？

**参考回答：**

我做 POC 测试时不会只堆高危攻击样本，因为那样测出来的结果往往不真实。我更倾向于按场景和风险类型去设计测试集。

一般会包括几类内容。第一类是正常业务白样本，用来测试误报和业务可用性。第二类是明确攻击样本，比如直接 prompt injection、越狱、敏感信息套取。第三类是对抗样本，比如伪装表达、混淆表达、边界样本。第四类是和现代 LLM 应用更相关的样本，比如 RAG 间接注入、检索污染。必要时还会补充场景化样本，比如办公助手、知识库问答、代码助手等。

这样设计的原因是，POC 阶段不能只证明系统“能打中最明显的攻击”，还要证明它在真实场景下既有拦截能力，也有可用性和可解释性。

### 14. 你做 POC 或策略对比时最关注哪些指标？

**参考回答：**

我通常会分三层来看。

第一层是效果指标，比如 precision、recall、F1，以及不同攻击类型下的表现。这一层回答的是“拦得准不准、漏得多不多”。

第二层是运营指标，比如 allow、review、block 的分布，误报率、漏报率和人工复核率。这一层回答的是“这套策略实际能不能用，会不会把人工复核压垮，业务能不能接受”。

第三层是解释性指标，也就是典型误报漏报案例、命中规则、根因类别和修复建议。这一层回答的是“为什么会这样，后续怎么调”。

我觉得真正的 POC 比较，不是只报一个总分，而是同时回答效果、可用性和可运营性这三件事。

### 15. 你怎么理解 RAG 间接注入？

**参考回答：**

我理解的 RAG 间接注入，本质上是攻击源转移了。传统 prompt 攻击通常来自用户输入，而 RAG 间接注入里，用户问题本身可能完全正常，真正的恶意指令藏在外部知识源、检索片段或者文档内容里。

这意味着如果系统只盯着用户输入，很可能会漏掉这类风险。所以我在项目里会单独考虑检索上下文这条链路，并把它和场景绑定起来看。比如知识库问答场景下，如果检索内容出现了明显的注入指令，那么系统应该更保守地处理。

这个点很值得在面试里讲，因为它能体现你对 LLM 应用安全的理解不是停留在“敏感词检测”，而是理解了现代应用架构里的真实攻击面。

### 16. 你觉得这个项目最贴合 JD 的部分是什么？

**参考回答：**

我觉得最贴合的是四块。

第一块是误报漏报分析。项目里不是只做检测，而是继续做归因和修复建议，这和 JD 提到的案例分析和归因是直接对应的。

第二块是样本库建设。我不仅整理攻击样本，还考虑对抗样本、白样本、边界样本和样本标签治理，这和 JD 提到的样本整理、分类和标签化高度一致。

第三块是规则、阈值和策略优化。项目里有多策略评测和阈值扫描，能支撑策略调优。

第四块是文档输出。项目里有测试报告、周报、复盘、案例和 SOP，这和 JD 里的分析文档、测试报告、运营分析材料也很匹配。

如果要再压缩成一句话，我会说：这个项目不是偏“写功能”，而是偏“把安全运营流程做出来”，这正好和岗位定位一致。

### 17. 你在这个项目里有哪些和 Python、数据分析相关的工作？

**参考回答：**

这个项目里我用 Python 做的事情主要集中在三类。

第一类是样本处理，比如样本导入、样本结构化、标签字段管理、样本质量审计。

第二类是评测和分析，比如批量跑样本、统计 precision、recall、F1、误报率、漏报率、人工复核率，做阈值扫描和策略对比。

第三类是文档自动化输出，比如把评测结果、误报漏报案例和后续建议整理成 Markdown 报告、周报和复盘文档。

我觉得这也和 JD 里提到的“具备基础的数据分析或脚本能力，能够协助进行日志分析、样本处理”比较一致。虽然这里不是传统意义上的日志分析，但本质上做的事情很接近，都是用脚本去自动化整理数据和输出分析结果。

### 18. 你怎么证明这个项目不只是 demo？

**参考回答：**

我不会硬说它已经是生产系统，但我会强调它已经超过了“只演示一次检测”的 demo 阶段。

一个普通 demo 往往只会展示输入一段 prompt，然后输出“安全/不安全”。但这个项目已经往前和往后都延伸了。往前，我做了样本治理和标签体系；往后，我做了批量评测、误报漏报归因、规则分析、案例中心和文档输出。这说明项目关注的不只是结果本身，还关注如何持续优化这套策略。

所以我通常会把它定位成“安全运营平台雏形”。它的亮点不是检测能力已经极致，而是已经具备了工程化和运营化思路。

### 19. 这个项目最大的不足是什么？

**参考回答：**

我会比较主动地承认三点不足。

第一，当前的检测能力还是以规则和基线模型为主，对复杂语义变形、强对抗样本的泛化能力还有限。

第二，虽然项目做了阈值扫描和策略对比，但离真正成熟的校准和线上反馈闭环还有距离。现在更多还是离线评测驱动。

第三，项目更偏平台和运营流程建设，真实大规模流量、线上压测、客户现场数据验证这部分还没有完全覆盖。

不过我会补一句，我觉得这几个不足本身也很正常，因为它们恰好对应了如果继续往下做，最值得投入的方向。

### 20. 如果继续做下去，你下一步会怎么优化？

**参考回答：**

如果继续做，我会优先补三件事，而且和项目早期路线不一样，不会再把主要精力放在“多加几条规则”上。

第一，继续做 residual 数据工程。尤其是中文 `harmful_operational_guidance_unstructured` 这类 hardest tail，我会系统性扩充：

1. 正样本：
   - 目标结果导向
   - 场景包装导向
   - 对比评估导向
   - 改写包装导向
   - 教程/方案/准备导向
2. 负样本：
   - 安全评估
   - 风险讨论
   - 课程大纲
   - 研究报告
   - 剧情/游戏/设定文本
   - 合法密码学和安全教育内容

第二，继续增强二阶段语义模型，而不是主要再堆关键词规则。因为当前最难的样本已经不是规则盲区，而是“非结构化但有可执行意图”的语义问题。

第三，继续细化分场景策略。比如办公助手、知识库问答、support assistant、RAG 场景，它们对误报和漏报的容忍度不一样，不能长期共用同一套 review / block 逻辑。

如果从岗位视角来说，这三件事也刚好对应了样本建设、策略优化和能力演进，而且比继续小步调堆规则更像真实的长期路线。

## 追问题与展开答法

### 1. 你为什么说这是 LLM Firewall，而不是普通内容安全项目？

**参考回答：**

因为普通内容安全更偏向判断“生成内容是否违规”，而 LLM Firewall 更关注模型交互链路里的攻击和操控风险，比如 prompt injection、越狱、系统提示词套取、工具滥用、RAG 间接注入等。我的项目关注的不只是输出，还包括输入和检索上下文，所以更接近 LLM Firewall。

### 2. 你怎么回答“这些阈值是不是拍脑袋定的”？

**参考回答：**

我不会说它完全不是经验值，因为早期项目里一定会有经验成分。但我会强调，阈值不是随便定的，而是基于离线评测、不同阈值扫描结果和场景风险偏好做的小步调优。重点不是把它包装成完美答案，而是说明我有评测方法、有前后对比、有业务解释。

### 3. 误报和漏报哪个更严重？

**参考回答：**

我不会给固定答案，而是会强调分场景看。对高风险场景，比如知识库问答、带工具调用的应用，漏报通常更危险；但对用户量很大的普通业务场景，误报会直接影响使用体验和业务接受度。所以真实策略设计通常不是绝对追求某一个指标，而是结合风险等级和运营成本做平衡。

### 4. 如果面试官说“你这个项目工程有点多，和岗位会不会不匹配”，你怎么回答？

**参考回答：**

我会说，我做工程不是为了炫技术栈，而是为了把安全运营流程真正落下来。比如样本库、批量评测、误报漏报归因、周报和 SOP，这些事情如果没有一些工程化支撑，其实很难持续做。这个岗位本身也不是纯研究岗，而是强调运营支持、样本处理、POC 测试和文档沉淀，所以我觉得这种工程化恰好是在为岗位需求服务。

### 5. 你在这个项目里最能体现“逻辑清晰”的地方是什么？

**参考回答：**

我觉得是我没有把问题笼统地说成“效果不好”，而是会拆成样本问题、规则问题、阈值问题和场景问题。每一类问题又有对应的分析方法和优化动作。比如误报不一定改规则，也可能先看白样本质量；漏报不一定只是补规则，也可能要补上下文样本或调整场景策略。我觉得这种拆解方式能体现我在做项目时是按流程和因果链路来思考的。

## 面试时的推荐讲法

如果面试官让你做项目介绍，推荐顺序如下：

1. 先讲项目定位：这是一个 LLM Firewall 运营平台雏形。
2. 再讲实现流程：检测对象定义、检测基线、样本库、评测、归因、优化、文档沉淀。
3. 再讲和 JD 的关系：误报漏报分析、样本整理、POC、报告输出。
4. 最后讲一个误报案例和一个漏报案例。

你可以直接用下面这段作为 1 分钟版本：

我做的是一个面向大模型应用的 LLM Firewall 评测与安全运营平台雏形。项目不是只做一次风险识别，而是把输入、检索上下文和模型输出都纳入检测范围，并用规则、基线分类器和输出过滤做组合判定。除了检测本身，我还建设了攻击样本、对抗样本和白样本样本库，补了样本质量审计、批量评测、误报漏报归因、规则效果分析和阈值扫描，最后把结果沉淀成测试报告、案例和 SOP。它最贴合这个岗位的地方在于，不只是做检测，而是把 LLM Firewall 的运营闭环做出来了。

## 最后提醒

面试时尽量少说这些内容：

1. 少按代码文件顺序讲。
2. 少花太多时间讲框架选型。
3. 少把重点放在“我写了哪些接口”。

面试时尽量多说这些内容：

1. 为什么这个项目要这样设计。
2. 你怎么一步步把它做成运营闭环。
3. 你怎么分析误报漏报并落到动作。
4. 你怎么做样本治理、POC 和文档沉淀。
5. 这些内容和 JD 是怎么一一对应的。
