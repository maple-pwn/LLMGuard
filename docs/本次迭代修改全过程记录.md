# 《本次迭代修改全过程记录》

## 1. 任务起点与整体演化

这次迭代最初并不是一次单点修补，而是从“做一个能运行、能评测、能展示的 LLM Firewall 项目”开始，逐步演化成“带在线网关、异步运营、租户隔离、RBAC、外部 benchmark 接入与策略持续优化能力的平台化系统”。

整个过程大致经历了五个阶段：

1. **第一阶段：从零搭建可运行闭环。**
   最初目标是完成一个完整的展示型项目：后端服务、规则引擎、基线分类器、样本库、评测脚本、报告生成、前端展示、测试与文档。对应仓库早期提交主要是 `76d1b17 chore: bootstrap LLM firewall app skeleton` 和 `35042b4 feat: add detection services and ops scripts`，以及后续的大量未提交增量改动。

2. **第二阶段：连续安全返工。**
   第一版完成后，马上暴露出未鉴权、本地文件读取、同步重计算、模型加载信任锚不稳、报告路径写入、配置占位密钥、输入长度与 DoS 面等问题。随后连续几轮都在做安全加固和接口/配置修补。

3. **第三阶段：从“评测演示系统”转向“生产化骨架”。**
   用户明确提出系统定位需要切到“在线防护网关 + 异步运营平台 + 人工复核闭环”。这触发了架构层调整：路由拆分为 `gateway/ops/admin`，引入 `Tenant/Application/PolicyBinding/TaskRun/ReviewTask/AuditLog/AlertEvent`，数据库开始向 PostgreSQL + Alembic 迁移，异步任务体系从数据库轮询逐步演化到 Redis/Arq 兼容骨架。

4. **第四阶段：多人协作与租户隔离。**
   在生产骨架有了以后，纯 API key 管理面不再够用，于是引入 `User / Role / Permission / Membership + JWT`，接着又修正了“全局权限并集导致跨租户提权”“样本库未租户隔离”“复核任务 scope 可空或冲突”的问题。

5. **第五阶段：外部 benchmark 驱动的英文覆盖补强。**
   当系统骨架稳定后，开始引入真实公开数据集做压力测试，先后接入 `neuralchemy/Prompt-injection-dataset`、`BIPIA`、`Unified-Prompt-Guard`、`Strata-Sword`。这把问题从“项目能不能跑”切换成“当前规则和分类器到底能不能在公开基准上看见攻击”。后续多轮几乎都围绕 benchmark 驱动的英文覆盖补强、误报压制和评测切片修正展开，最终把英文直攻从明显盲区推进到了可用覆盖。

当前最终状态是：

- 系统已经不是最初的 SQLite 单机演示台，而是具备生产化雏形的 **网关 + 异步运营 + RBAC + 租户隔离** 架构。
- 数据面已经支持 **外部数据集独立导入、元数据保留、中英分开评测、英文直攻专项切片**。
- 检测策略上，`neuralchemy` 英文直攻切片已经从早期的几乎不可见，推进到 `run_29` 的 `Recall=0.761 / F1=0.864 / FPR≈0.003`。
- 下一步不再是“补大坑”，而是进入 **残余漏报聚类与尾部清理** 阶段。

> 说明：以下轮次时间线主要依据三类证据恢复：  
> 1）本次会话中的需求变化、返工反馈与结果确认；  
> 2）仓库当前文件与未提交 diff；  
> 3）`docs/reports/run_*.md`、`pytest` 结果、`git log` 提交记录。  
> Git 记录本身不够细，后半段很多轮次属于“根据修改痕迹 + 报告文件 + 会话记录推断”。

## 2. 按轮次展开的详细修改记录

## 第1轮迭代

### 1）触发原因

初始需求是从零在当前仓库中开发一个“面向大模型应用的 LLM Firewall 评测与运营系统”，要求覆盖样本导入、规则检测、分类器、批量评测、误报漏报归因、Markdown 报告、文档和前端展示。

### 2）本轮目标

交付最小可运行闭环：`样本导入 -> /scan 检测 -> 结果入库 -> 批量评测 -> 报告生成 -> 前端展示`。

### 3）本轮实际修改内容

- `app/main.py`、`app/api/routes.py`：新增 FastAPI 入口与基础 API。
- `app/ui.py`：新增 Streamlit 管理页，提供基本可视化展示。
- `core/bootstrap.py`、`core/database.py`、`core/config.py`：建立启动引导、数据库初始化、配置加载。
- `models/entities.py`、`models/schemas.py`：定义 `Sample / EvaluationRun / DetectionResult / Rule / StrategyConfig` 等基础模型。
- `services/rule_engine.py`：实现 YAML 规则加载、命中解释。
- `services/classifier.py`：实现 TF-IDF + 逻辑回归基线分类器。
- `services/detection.py`：实现规则 + 分类器 + 策略判决。
- `services/evaluation.py`、`services/attribution.py`、`services/reporting.py`：实现批量评测、归因、报告生成。
- `scripts/*.py`：补齐 `init_db.py`、`seed_data.py`、`train_classifier.py`、`run_evaluation.py` 等脚本。
- `data/samples/*.jsonl`：加入中文攻击样本、白样本、RAG 间接注入样本。
- `README.md`、`docs/*.md`：补齐安装、运行、POC 说明、样本标注规范、项目讲解稿。

修改性质：**新增 + 初始化 + 搭建闭环**。

### 4）修改结果

项目第一次具备完整运行链路，可以启动 API、导入样本、训练模型、跑评测并生成报告。早期报告产物可见 `docs/reports/run_3.md`、`docs/reports/run_4.md`。

### 5）本轮遗留问题与新暴露问题

- 管理面和扫描接口都没有鉴权。
- 评测和样本审计都是同步重计算。
- SQLite + 本地文件产物更适合单机演示，不适合多人使用。
- 模型加载、输入大小、样本导入和报告生成存在明显安全面。

### 6）进入下一轮的原因

项目虽然能跑，但马上进入安全审视阶段；首轮主要问题是“它能运行，但不安全”。

## 第2轮迭代

### 1）触发原因

第一轮交付后收到集中审计反馈：核心接口全裸奔、`/evaluate` 可读本机文件、`joblib.load` 存在不安全反序列化、输入和计算量无上限、异常路径会留下脏状态、检测数据明文落库。

### 2）本轮目标

先把演示版里最明显的高危问题收口，让系统至少达到“可展示但不明显裸奔”的状态。

### 3）本轮实际修改内容

- `app/api/routes.py`：为 `/scan` 与管理接口补 API key 级鉴权；移除客户端可控 `source_path`；限制导入和评测参数。
- `core/security.py`：新增 API key 校验依赖。
- `models/schemas.py`：对扫描、导入、评测请求补充长度和数量上限。
- `services/evaluation.py`：限制策略数量、评测样本数与计算量；异常时把 `EvaluationRun` 标记为 `failed`。
- `services/classifier.py`：为模型加载增加 SHA-256 校验。
- `services/detection.py`：默认不落敏感原文，增加脱敏/截断。
- `services/rule_engine.py`：为规则热加载补 schema 校验与 regex 预检。
- `README.md`、`.env.example`：补充鉴权、哈希、限制说明。

修改性质：**安全修补 + 输入约束 + 风险收敛**。

### 4）修改结果

系统不再直接暴露高危管理能力；`/evaluate` 去掉了本地文件读取面；模型校验、异常处理和导入上限也补上了。测试数在这一阶段提升到约 `11-13 passed`。

### 5）本轮遗留问题与新暴露问题

- 默认 API key 仍是公开占位值。
- 模型 SHA-256 仍可从同目录 sidecar 读取，无法防同权限篡改。
- 评测仍然同步执行。

### 6）进入下一轮的原因

安全审计继续指出占位密钥和 sidecar hash 这两项会让“看起来加固过”的逻辑退化成伪安全。

---

## 第3轮迭代

### 1）触发原因

第二轮加固后，用户继续指出：

- `SCAN_API_KEY` / `ADMIN_API_KEY` 默认值公开可猜。
- 模型哈希校验若依赖同目录 `.sha256` sidecar，无法构成真正的独立信任锚。

### 2）本轮目标

让“鉴权”和“模型完整性”都真正依赖独立可信配置，而不是仓库内占位值或同目录 sidecar。

### 3）本轮实际修改内容

- `core/config.py`：拒绝占位密钥启动；把环境读取改为实例化时生效，而不是模块导入时固化。
- `core/security.py`、`app/main.py`：启动时强制校验真实密钥。
- `services/classifier.py`：移除 sidecar 回退逻辑，只接受 `MODEL_SHA256`。
- `scripts/train_classifier.py`：训练后输出真实模型哈希。
- `tests/test_api_security.py`、`tests/conftest.py`：补充占位密钥拒绝、哈希校验测试。
- 后续又追加一轮小修补：拒绝 `.env.example` 中新示例值 `replace-with-real-*`，并加入模板串与最小长度检查。

修改性质：**安全语义修正 + 配置加载修补**。

### 4）修改结果

应用在未提供真实密钥或使用示例值时会拒绝启动；模型完整性校验只信任环境变量。测试推进到 `12-13 passed`。

### 5）本轮遗留问题与新暴露问题

- 系统仍然是“评测台主导”，不是在线网关。
- 权限仍停留在 API key 层级，不支持多人协作。

### 6）进入下一轮的原因

基础安全项收住后，开发重心转到“把系统从单一评测工具拓成更完整的运营分析平台”。

用户提出“第二轮增强开发”，要求把项目从基础版推进成更贴近安全运营场景的数据分析与策略优化平台。

### 2）本轮目标

增强样本质量治理、规则效果分析、案例中心、多策略对比、周报/复盘生成和前端运营展示。

- `services/sample_audit.py`、`scripts/audit_samples.py`：实现样本质量审计。
- `services/rule_analysis.py`、`scripts/analyze_rule_effectiveness.py`：实现规则效果与贡献分析。
- `services/casebook.py`、`scripts/build_casebook.py`：实现误报漏报案例中心与案例文档生成。
- `services/compare.py`、`scripts/compare_strategies.py`：实现多策略横向对比。
- `services/ops_reporting.py`、`scripts/generate_weekly_report.py`、`scripts/generate_postmortem.py`：实现周报与复盘产物。
- `app/ui.py`：加入“项目概览 / 样本复核 / 规则运营分析 / 案例中心 / 策略对比 / 单样本分析 / 报告中心”。
- `docs/二期增强说明.md`、`docs/项目讲解稿.md`、`README.md`：补齐二期文档。
- `data/samples/boundary_attack_samples.jsonl`、`mixed_complex_samples.jsonl`、`tricky_benign_samples.jsonl`：补样本。

修改性质：**新增 + 平台功能扩展 + 前端增强**。

### 4）修改结果

系统从单纯“能扫能评”扩展成了“样本治理 + 规则运营 + 案例沉淀 + 周报复盘”的运营分析平台。阶段性代表产物为：

- `docs/reports/run_7.md`
- `docs/reports/sample_audit_20260416_141921.md`
- `docs/reports/rule_effectiveness_20260416_142023.md`
- `docs/cases/casebook_20260416_142023.md`
- `docs/weekly_reports/phase2_weekly_report_20260416_142023.md`
- `docs/postmortems/phase2_postmortem_20260416_142023.md`

### 5）本轮遗留问题与新暴露问题

- 新增了更多报告与文件生成路径，也带来了新的路径写入风险。
- 样本审计是同步全量比较，平方级开销可能成为新 DoS 面。
- 管理面仍然没有真正的用户/角色体系。

### 6）进入下一轮的原因

二期功能落地后，新的安全与资源控制问题立刻暴露，需要回头补治理面的边界条件。

## 第5轮迭代

### 1）触发原因

二期增强后被指出新的安全问题：

- `/reports/weekly` 与 `/reports/postmortem` 的 `title` 可控且未净化，存在越界写文件。
- `/evaluations/compare` 坏输入会打 500。
- schema 里 `MAX_*` 限制仍可能因导入时快照不生效。
- 样本审计是同步平方级计算，没有上限。

### 2）本轮目标

把新加的运营能力补齐路径安全、输入校验和资源上限，避免“分析页越多，攻击面也越多”。

### 3）本轮实际修改内容

- `services/ops_reporting.py`：对标题做路径净化与安全文件名限制。
- `app/api/routes.py`：把 `/evaluations/compare` 的坏输入从 500 改成 400。
- `models/schemas.py`：把部分长度限制改成运行时校验，不再依赖导入期快照。
- `core/config.py`、`services/sample_audit.py`、`scripts/audit_samples.py`、`app/ui.py`：为样本审计增加样本数和 pairwise 比较上限。
- `tests/test_api_security.py`、`tests/test_phase2_services.py`：补充回归测试。

修改性质：**安全修补 + 输入校验 + DoS 收敛**。

### 4）修改结果

报告文件无法再借标题穿越目录；审计接口不再接受无限计算；比较接口对坏 `run_ids` 返回 4xx。阶段性测试结果为 `22 passed`。

### 5）本轮遗留问题与新暴露问题

- 运营能力虽然更强，但系统整体仍偏“分析台”定位。
- 后台重任务仍在同步链路或数据库轮询 worker 中运行。

### 6）进入下一轮的原因

用户明确提出：如果要从“可演示项目”变成“可直接上线用的系统”，必须先重构成在线网关 + 异步运营平台。

## 第6轮迭代

### 1）触发原因

用户重新定义项目定位：要把系统从“评测与运营台”拆成“在线防护网关 + 离线运营平台 + 人工复核闭环”。

### 2）本轮目标

完成第一步架构转向：把在线扫描和离线运营解耦，并为 PostgreSQL、异步任务、租户/应用/策略绑定打骨架。

### 3）本轮实际修改内容

- `app/api/gateway.py`、`app/api/ops.py`、`app/api/admin.py`：把路由拆成在线、运营、管理三组。
- `models/entities.py`：新增 `Tenant / Application / PolicyBinding / TaskRun / ReviewTask / AuditLog / AlertEvent`。
- `services/task_queue.py`、`scripts/run_worker.py`：引入 worker 骨架，重计算接口改成 job 风格。
- `services/detection.py`：把 `/gateway/scan` 变成基于 `tenant_slug + application_key + environment` 的策略解析入口。
- `core/bootstrap.py`、`core/database.py`：开始兼容 PostgreSQL 场景。
- `alembic.ini`、`alembic/env.py`：补 Alembic 环境。
- `README.md`：更新为“Gateway & Ops Platform”定位。

修改性质：**结构重做 + 架构分层 + 生产骨架搭建**。

### 4）修改结果

系统从路由组织到数据模型都不再是单体评测台，而开始具备“网关 + 后台”的雏形。此阶段测试结果达到 `25 passed`。

### 5）本轮遗留问题与新暴露问题

- 数据库驱动的 worker 存在任务重复领取风险。
- `/gateway/scan` 在找不到绑定时仍会回退默认策略，属于 fail-open。
- Alembic 与 `create_all()` 并存，存在 schema 漂移隐患。
- 绑定关系缺少租户一致性校验。

### 6）进入下一轮的原因

架构骨架一旦立起来，原来的“展示版容忍度”就不够了，必须立即修生产语义上的一致性问题。

## 第7轮迭代

### 1）触发原因

对生产语义进行审查后暴露了几个高优先级问题：

- 任务领取不是原子操作。
- 网关策略绑定是 fail-open。
- PostgreSQL 下仍在启动期改 schema。
- `policy binding` 允许跨租户脏绑定。

### 2）本轮目标

把“生产骨架”的关键语义补到位，避免刚引入的新模型和新路由被旧习惯打穿。

### 3）本轮实际修改内容

- `services/task_queue.py`：数据库后备模式领取任务改成 compare-and-set。
- `services/detection.py`、`app/api/gateway.py`：网关在未解析到合法绑定时 fail-closed。
- `core/database.py`、`core/bootstrap.py`、`core/migrations.py`：在 PostgreSQL 场景停用启动期 `create_all()` 和 SQLite patch。
- `app/api/admin.py`：创建 `policy binding` 时校验 `application_key` 属于指定租户。
- `scripts/demo_scan.py`、`app/ui.py`：适配新的租户/应用/环境参数。

修改性质：**修补 + 生产语义收口**。

### 4）修改结果

生产网关开始真正按 `PolicyBinding` 工作；数据库启动行为不再绕过迁移管理；跨租户脏绑定被拒绝。测试推进到 `29 passed`。

### 5）本轮遗留问题与新暴露问题

- 任务队列仍是数据库轮询为主，不适合真正的生产负载。
- 任务幂等和消息投递恢复还不够稳。

### 6）进入下一轮的原因

用户建议第一优先级改为“先切 Redis + Arq/Celery，再补 RBAC”，因此任务系统继续往正式队列演进。

---

## 第8轮迭代

### 1）触发原因

用户给出明确下一步：先把任务队列切到 Redis，再补 Alembic 正式迁移。

### 2）本轮目标

从数据库轮询 worker 过渡到可切换的异步任务后端，并把 schema 正式固化成第一版迁移。

### 3）本轮实际修改内容

- `core/queue.py`：新增队列抽象与后端配置。
- `services/task_queue.py`、`services/task_registry.py`：把任务提交与执行拆开，为 Arq 接入做准备。
- `scripts/run_worker.py`：改为兼容新队列骨架。
- `models/entities.py`：为 `TaskRun` 增加 `queue_backend / backend_job_id / idempotency_key / attempts / max_retries / timeout_seconds / execution_log / last_heartbeat_at`。
- `alembic/versions/20260416_01_initial_platform_schema.py`：生成首版正式迁移。
- `.env.example`、`README.md`：加入 Redis/Arq 配置说明。

修改性质：**结构调整 + 基础设施升级**。

## 3. 本次迭代中的关键转折点

### 转折点 1：从“能运行”转向“先收口安全”

第一版完成后，最初看起来只是一个功能项目，但高危问题很集中：未鉴权、LFI、DoS 面、模型加载信任锚不稳、敏感数据明文落库。这个阶段的判断直接把开发顺序从“继续堆功能”切成了“先把系统做成不裸奔的状态”。

### 转折点 2：从“评测台”转向“在线网关 + 异步运营平台”

这是整个迭代里最重要的定位切换。用户明确指出：如果要落地，核心不是继续堆报表，而是重构成在线防护网关、异步任务平台和人工复核闭环。之后的路由拆分、租户模型、任务队列、Alembic、RBAC，都是围绕这个转向发生的。

### 转折点 3：从“有 RBAC”到“真正 tenant-scoped”

最初加了 JWT 和角色以后，系统表面上已经“像一个平台”，但很快暴露出全局权限并集和全局样本库的问题。把权限与样本都改成租户内生效，才让“多人协作的正式产品”真正成立。

### 转折点 4：从“功能完善”转向“公开 benchmark 驱动”

接入 `neuralchemy` 和 `BIPIA` 后，项目第一次有了外部、可复现的策略基线。这个阶段把问题从“系统是否完整”转成了“它在公开基准上能不能看见攻击”，直接驱动了后续几乎所有英文优化工作。

### 转折点 5：从“高召回实验策略”回到“可灰度上线策略”

`run_14` 和 `run_22` 都出现过一种典型现象：召回很猛，但误报也高到无法上线。真正的方向修正不是继续拧阈值，而是白样本补强、结构特征 gating、hard negative、专项切片和定点补强。这一点在 `run_15` 和 `run_26` 得到了验证。

### 转折点 6：从“看总 Recall”转向“看专项子切片”

`run_28` 之前，`English direct injection Recall` 还是一个大盘指标。把它拆成 `PWNED variants / Payload rewrite / Obfuscation / Backslash separator smuggling` 后，后续优化才真正变成可定位、可解释的定点工作。`run_29` 的大幅提升，本质上来自这一轮“先把问题拆明白”。
